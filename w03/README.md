# w03 — RAG(BM25 + 引用 + 拒答)

只用標準庫:依 markdown 標題切段、手寫 BM25(英文單字 + 中文 bigram)、分數門檻、帶 chunk 引用驗證與重試的回答、retrieval 評估。語料是私人 markdown 筆記庫;索引與考題放在 gitignored 的 `corpus/`,本文件只列彙總數字。

```bash
python3 -m rag ask "問題"   # 回答 + 引用的 chunk id
python3 -m rag eval         # recall@k、MRR、gated、拒答率
```

## 設定
CHUNK_MAX_CHARS=800、CHUNK_OVERLAP_CHARS=100、BM25 k1=1.5 / b=0.75、TOP_K=5、MIN_SCORE_TO_ANSWER=5.0、MAX_RETRIES=3

## 驗收
- 門檻校準:先用長問句校準為 10(有答案 15.0–26.4、無答案 6.1–8.2);人工測短問句時,有答案的第 1 名只有 8.4 / 約 10.0,與無答案區間重疊 → 降到 5,改由 LLM 判斷是否拒答 ✓
- 引用驗證:假 call_llm 先回不存在的 chunk id → 被擋下並帶錯誤回饋重試,第 2 次成功;連續失敗 4 次拋 AnswerError ✓
- 無答案題 3/3 回「資料不足」(門檻 5 下全部由 LLM 拒答,沒有編造)✓
- 5 題已知答案:4/5 答案正確且引用 chunk 含該資訊(人工核對);1 題檢索漏掉正解,LLM 正確拒答 ✓
- eval(20 題:17 題有答案,其中 5 題換說法、3 題短問句;3 題無答案):

| CHUNK_MAX_CHARS | chunks | 平均 tokens/chunk | recall@5 | MRR | gated | 拒答率 |
|---|---|---|---|---|---|---|
| 267(×1/3) | 2003 | 87 | 0.82 | 0.65 | 0/17 | 1.00 |
| **800** | 786 | 152 | 0.88 | **0.75** | 0/17 | 1.00 |
| 2400(×3) | 615 | 181 | 0.88 | 0.75 | 0/17 | 1.00 |

## 心得
- ×3 沒有變化:先依標題切段,多數章節本來就 < 800 字,上限只影響少數長章節(chunks 786 → 615)
- ×1/3 讓 recall 0.88 → 0.82、MRR 0.75 → 0.65:一段完整的說明被切碎,單塊分數不夠高;BM25 的長度正規化又偏好短 chunk,別處的碎片會把正解擠出前 5 名
- 漏網題有兩類,調 chunk 大小都救不了:「筆記用英文術語、問題用中文描述概念」與「口語說法對不上筆記用詞」,字面對不上 → 需要 embedding / hybrid
- 題目直接用標題字時 recall=1.00、MRR=0.88,高估了檢索能力;換說法與短問句才拉出差距
- BM25 分數隨問題長度變化,固定的絕對門檻對短問句太嚴:檢索已把正解排第 1,卻被判成「無相關資料」。門檻只適合擋明顯無關的問題,有沒有答案交給 LLM 判斷
- 調大的代價 eval 量不到:2400 字 × top-5 ≈ 12k 字的 context,成本與雜訊都上升 → 維持 800
- `_check` 只驗格式與 id 存在,不驗忠實度:曾出現引用了真的 chunk 卻寫出原文沒有的內容,只能靠人工核對或 LLM-as-judge
